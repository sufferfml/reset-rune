# Windows 版开发计划

状态：设计方案，尚未实现或发行 Windows 版本。依据当前仓库和官方文档编制，核对日期为 2026-11-06。下文工期、资源预算和目录均为开发目标，不能当作实测结果。

配套文档：[技术方案](windows-technical-design.md) · [现有验证范围](acceptance-matrix.md)。

## 1. 产品目标与范围

把 Bottled Reset Rune 做成一个可直接安装、安静常驻的 Windows 小工具。用户核对 Codex 账号并开启自动使用后，工具在备用重置到期前按设定提前量尝试使用。Windows 版应提供完整托盘界面、后台、CLI、安装卸载与故障恢复，不能把只能运行的命令行原型当成交付。

宣传主句沿用：

- 中文：把codex的重置变成神符装进魔瓶
- English: Turn your Codex resets into bottled runes.

宣传后紧接实际用途说明：用户开启后，在 Codex 备用重置过期前自动尝试使用。它不增加额度、不保证服务端接受兑换，也不阻止电脑睡眠。

### 发行范围

| 阶段 | 交付范围 | 放行条件 |
| --- | --- | --- |
| A：完整 x64 版 | Windows 11 x64；原生 Windows Codex；完整托盘、设置、记录、CLI、安装与恢复 | 核心合同、可靠性、资源和真实 Windows 交付验收通过 |
| B：环境与架构扩展 | Windows 11 ARM64 原生载荷；可选择 WSL2 发行版内的 Codex 登录与运行时 | ARM64 实机、WSL 子进程回收、身份切换及同机单执行器验收通过 |
| 后续可选 | Microsoft Store、winget、其他系统版本 | 有明确用户需求，再单独评估渠道规则及维护成本 |

A 阶段具有完整产品能力；B 阶段增加运行环境覆盖，不增加兑换次数或改变业务规则。Windows 10、Windows Server、32 位 x86、远程机器和多账号同时保护不列入此次发行承诺。不能把 ARM64 仿真运行当作 ARM64 原生验收。

### 功能清单

| 功能 | Windows 交付要求 |
| --- | --- |
| 账号 | 通过所选环境的官方 Codex 复用登录；开启前确认账号及工作区；身份变化停止自动操作 |
| 自动使用 | 默认关闭；提前量 5 / 10 / 30 / 60 分钟，默认 10 分钟；可随时暂停 |
| 库存 | 显示重置神符数量与最近到期时间，区分有符、空瓶与待确认 |
| 展开区 | 显示重置神符图与明细、额度蓝量条、尝试时机与战报 |
| 设置 | 默认英文，可选简体中文；跟随系统 / 浅色 / 深色；登录启动与通知可选 |
| 后台 | 关闭面板或退出托盘界面后，已开启的后台仍可运行；暂停停止周期任务；停止后台是独立动作 |
| CLI | `status`、`refresh`、`ui`、`enable --confirm`、`bind --confirm`、`pause`、`config`、生命周期管理和隔离模拟 |
| 分发 | GitHub Release 的用户级 EXE 安装包与 ZIP；npm 薄入口和对应 Windows 平台包 |

同账号、同工作区和同额度池的 DSH 消耗由 Codex 账户读数自然覆盖，不建设 DSH 请求监听器。只有可复用的登录或运行时位于 WSL 时，才需要选择 WSL 运行环境；这两件事不能混为一谈。

## 2. 技术路线

采用 **Rust 原生执行核心 + Win32 托盘与紧凑面板 + 用户会话内后台 + SQLite 持久化**。保留现有 Swift macOS 版，双方共享业务合同、测试向量、主题素材和公开命令语义。

当前仓库的产品界面是 SwiftUI，没有可直接复用的网页前端。因此不把 Tauri 的“复用网页”当作选型收益；也不为 Windows 交付再次替换 macOS 技术栈。交互控件使用真实 Windows 控件，魔瓶、蓝量条等展示元素可自绘，避免整块画布造成键盘和辅助功能返工。

以下问题在 P0 样机中冻结，未通过不得先堆完整界面：

1. 固定版本 Codex 在目标设备上的 stdio、账号读取和库存合同。
2. 原生面板、静态 SQLite 与所选 Windows API 的实际包体和空闲成本。
3. 标准用户身份能否可靠注册、运行和移除自己的后台任务。
4. 摘要、Unicode、整数及状态转换是否通过现有跨语言向量。

官方 0.153.0 已提供 Windows x64 / ARM64 可执行文件，不能再把“上游是否有 Windows 二进制”当作未知条件；目标设备的实际联调仍需验证。[上游固定版本](https://github.com/openai/codex/releases/tag/rust-v0.153.0)

## 5. 验收与发布门槛

### 业务与安全

- 默认关闭、手动刷新只读、开启需要确认；切换账号或运行环境不能沿用未经核对的授权。
- 同一账号和额度池只在一台设备开启自动使用；同机互斥不能协调其他 Windows、Mac 或 WSL 内独立安装的执行器，本期不建设云端协调服务。
- 意图提交成功后才能发送；成功回执先提交再重读。请求已写出后的超时、退出或断线不能按“确定未发送”处理。
- 重启恢复只使用原 credit ID 和原幂等键；未确认结果阻断后续目标。两个安装入口、重复启动或后台重启不得产生第二笔逻辑兑换。
- 所有自动化使用假时钟、合成账号、假 App Server 和独立 Windows 用户 / 目录。**禁止使用真实账号的备用重置测试。**
- 目标设备只读联调需另行明确授权；模拟通过不代表服务端在低使用量时接受兑换。

### 生命周期与体验

- 普通用户安装不需管理员权限，不注册 SYSTEM 服务，不保存用户密码。
- EXE 与 npm 连接同一用户后台；移除下载来源不使后台指向失效路径。
- Codex 路径、所选环境的 home 和 WSL 用户在后台重启后保持明确；不能依赖首次打开应用时终端的临时环境。
- 登录启动、停止、卸载、升级失败恢复、原生回退全部有隔离回执；卸载保留操作记录和 Codex 登录。
- 关闭托盘不停止已授权的后台；Explorer 重启后图标恢复；高 DPI、多屏、任务栏位置、键盘、Narrator 和系统高对比可用。
- 唤醒后只处理已到期或此前失败的任务；跨过到期记为错过，不能事后兑换过期目标。

### 资源预算

下列是候选版本的目标，P0 和 P5 均需实测。常驻成本不包含按需启动的官方 Codex，后者必须另外报告，不能藏入“应用很轻”的结论。

| 项目 | 目标 / 放行条件 |
| --- | --- |
| 远期完整库存 | 无周期远程查询；没有每秒刷新、常驻模型会话或动画 |
| 空闲 CPU | 前台面板关闭、无查询的 30 分钟观察中，后台与托盘合计平均不高于单核 0.1%；同时报告采样精度 |
| 内存 | 后台与隐藏托盘合计 Private Bytes 目标 ≤ 30 MiB；超出需定位并决定是否调整，不声称已经达到 |
| 包体 | 单架构完整下载目标 ≤ 10 MiB；超过 15 MiB 必须解释依赖和替代方案；不靠联网下载隐藏运行时体积 |
| 程序占盘 | 当前与上一可回退版本合计目标 ≤ 40 MiB；数据库与日志另列，不通过清除未决证据满足预算 |
| 运行观察 | 至少 24 小时开关 / 空库存 / 远期 / 临期合成场景；记录任务计划程序没有默认三天上限的配置，并做跨 72 小时运行抽查 |
| 临期调度 | 在线、未睡眠、无上游等待限制的假服务场景，计划触发偏差 p95 ≤ 2 秒；不宣传为 Windows 或 Codex 的实时 SLA |

### 发布清单

GitHub 和 npm 均准备完成后，先检查实际注册表与下载文件，再公开 Windows 可用说明。用户级安装包、ZIP、平台包和运行目录中的同架构签名程序必须对应同一构建；公布 SHA-256、版本、依赖许可和支持范围。Windows 签名不能承诺立即消除 SmartScreen 提示。[Microsoft 说明](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)

## 6. 风险、依赖与维护

| 风险 / 外部条件 | 处理方式 |
| --- | --- |
| Codex 协议或存储策略变化 | 固定版本与白名单；启动前检查兼容性，未知版本停止并提示；另做版本扩展验收 |
| 持久化或摘要差分失败 | P1 阻断；不以改测试期望掩盖语义差异，不降低持久性换取省电数字 |
| Task Scheduler 被企业策略禁用 | 明确说明后台不可用；不绕过策略或自动改为管理员 / SYSTEM |
| WSL 无可复用登录、凭据只在其他环境中 | 显示所选环境及官方登录指引；不搬运令牌，不承诺所有登录模式都零配置 |
| WSL 子进程不能可靠定向回收 | 不放行 B2，不用 `wsl --shutdown` 影响其他工作 |
| 原生深色控件或辅助功能不合格 | 优先使用可访问的标准控件，调整装饰；不把整个界面变成自绘画布 |
| 签名身份 / 硬件尚未准备 | P0 列为外部依赖，开发中并行准备；不以未签名包冒充正式交付 |
| 双实现逐渐漂移 | 每次业务合同变化同时跑 Swift、Rust 与共享向量；平台变化各自验证 |

不需要新增产品云服务器。实际资金支出主要是 Windows 测试设备或虚拟机环境及代码签名；可以评估开源签名服务，但资格与时间不能提前保证。签名方案和价格在发行前按当时官方信息核实，不写死为产品运行成本。

## 7. 开工顺序

先做 P0，并提供一个仅模拟、能展示托盘和资源采样的 Windows 样机，以及实际兼容性和存储结论。通过后依次完成 P1–P5；无需用户逐条批准已确认的实现细节。A 版完整验收后再合入 B1 / B2，避免把 WSL 和 ARM64 的独立风险掩盖在“Windows 已支持”一句话里。

本次文档交付不代表已经开始实现或发行 Windows 软件。技术边界、目录、IPC、数据与发布格式见[技术方案](windows-technical-design.md)。
